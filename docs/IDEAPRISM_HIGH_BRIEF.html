Onboarding Brief

IdeaPrism High
프로젝트 한눈에 보기

비개발자·신입 개발자용 브리핑입니다. “이 서비스 뭘로 만들었어요?” “어떻게 동작해요?” “어디가 약한가요?”에 바로 답할 수 있게 정리했습니다.

30초 답변 치트시트

IdeaPrism High는 학생 발명품을 검색하는 웹 서비스입니다. 원본 서비스(ideaprism.or.kr / ideaprism_sdg2)의 검색·상세·특허 기능을 가져와, 네 고등학교가 각자 코드로 들어가는 전용 화면으로 만든 MVP입니다. 기술적으로는 Next.js(React) + TypeScript + Supabase + Tailwind로 만들었고, 학교 코드가 맞으면 쿠키로 세션을 열고 그 학교 색·로고로 UI가 바뀝니다. 지금은 UI·입장 통제만 학교별이고, 발명 데이터는 아직 학교마다 완전히 분리되지 않은 상태입니다.

이게 뭐예요 뭘로 만들었나 사용자 흐름 구조 핵심 기능 개발 특징 취약점·리스크 용어집

1. 이게 뭐예요?

제품 관점 한 줄 + 왜 만들었는지.

제품 정의

고등학생이 키워드·SCAMPER·문제 유형으로 선배 발명품을 찾고, 고른 결과로 특허 검색식(KIPRIS)까지 이어가는 학습용 검색 서비스입니다.

이 버전(High)의 특별함

전국 공용 사이트가 아니라, 대광고 · 미래산업과학고 · 삼일공고 · 보성고 네 학교가 각자 코드로 들어와 자기 학교 브랜드 UI를 보는 형태입니다.

대상 학교와 입장 코드

학교 지역 코드 (예시) 역할
대광고등학교 부산 DAEGWANG 초록 계열 테마
미래산업과학고등학교 서울 MIRAE 네이비 계열 테마
삼일공업고등학교 수원 SAMIL 자주·금 계열 테마
보성고등학교 서울 BOSEONG 버건디 계열 테마

코드 값은 src/config/school-codes.ts에서 바꿉니다. 학교 이름·색·로고는 src/config/schools.ts와 public/schools/입니다.

2. 뭘로 만들었나? (기술 스택)

외부 미팅에서 “기술 스택이 뭔가요?”라고 물으면 이 표를 기준으로 말하면 됩니다.

  • Frontend Next.js 15 (App Router) + React 19 + TypeScript. 화면과 서버 API를 한 프로젝트에서 만듭니다.
  • Styling Tailwind CSS 4. 학교별로 CSS 변수(--primary 등)를 바꿔 테마를 입힙니다.
  • Data / DB Supabase (PostgreSQL). 발명품·태그·기관 코드 등이 들어 있는 클라우드 DB.
  • Client state TanStack React Query. 검색 결과 같은 서버 데이터를 브라우저에서 캐시·재요청.
  • External API KIPRIS 특허 검색. 선택적으로 OpenAI(채팅 관련 코드가 원본에서 남아 있음).
  • Motion / UI Framer Motion, Lucide 아이콘. 관리자 쪽에는 차트(Recharts), 워크플로(XYFlow) 흔적이 있습니다.
  • Origin 코드 베이스는 ideaprism_sdg2를 복사한 뒤, 학교 대문·세션·테마를 얹은 파생 프로젝트입니다.
비개발자용 비유: Next.js는 “웹사이트 건물”, React는 “방 안 가구를 그리는 방식”, Supabase는 “발명품이 들어 있는 창고(DB)”, Tailwind는 “페인트·인테리어 도구”, 학교 코드는 “교문 비밀번호”입니다.

3. 사용자가 보는 흐름

학생이 서비스를 쓰는 순서를 단계로 나눈 것입니다.

01 대문 학교 이름 목록 없이 코드만 입력
→
02 인증 서버가 코드 확인 후 쿠키 발급
→
03 학교 홈 로고·교훈·색으로 꾸며진 홈
→
04 검색·상세 발명 검색, 필터, 카드/상세
→
05 특허식 고른 발명으로 KIPRIS 검색식

입장(학교 세션)

  • 대문 컴포넌트: SchoolGate
  • API: POST /api/auth/school
  • 쿠키: httpOnly 세션 토큰 (약 12시간)
  • 나가기: 로그아웃 API가 학교·관리자 쿠키 삭제

막히는 길(보호)

  • middleware가 검색·발명·일부 API를 가드
  • 세션 없으면 대문으로 돌려보냄
  • 관리자(/admin)는 별도 관리자 세션

4. 구조 — 어떻게 짜여 있나

신입에게 “폴더 지도”와 “레이어”를 같이 보여주면 이해가 빠릅니다.

레이어 한 장 요약

브라우저 UI (React 컴포넌트) ← 학교 테마 CSS 변수 │ ▼ Next.js 페이지(app/) + API Route + middleware │ ├─ 학교 세션 쿠키 검증 ├─ 검색/특허 API └─ Supabase 클라이언트 │ ▼ Supabase DB inventions, tags, partner…

주요 폴더

src/app/ ← 페이지·API (URL과 1:1에 가깝게) page.tsx 홈 / 또는 SchoolGate search/ 검색 화면 inventions/[id]/ 발명 상세 api/auth/school/ 학교 코드 입장 api/search/ 발명 검색 API api/kipris/ 특허 검색 admin/ 관리자(원본에서 상속) src/components/ auth/SchoolGate.tsx 대문 school/ SchoolProvider, SchoolCrest features/ 검색·카드·상세·특허 UI layout/ Header, Footer src/config/ schools.ts 학교 프로필(이름·색·로고) school-codes.ts 입장 코드 (서버 전용 용도) src/lib/ school-token.ts 세션 토큰 서명/검증 school-session.ts 쿠키에서 학교 읽기 src/middleware.ts 진입 전 가드(문지기) public/schools/ 학교 로고 이미지 supabase/ 마이그레이션·엣지 함수 흔적

학교 UI가 바뀌는 원리

  1. 서버가 쿠키에서 학교 slug를 읽음 (getSchoolSession)
  2. layout.tsx가 그 학교 색을 HTML에 CSS 변수로 심음
  3. Header/홈/Footer가 useSchool()로 이름·로고를 표시

즉, 페이지를 네 벌 만든 것이 아니라, 한 벌의 앱에 “옷(테마)”만 갈아입히는 구조입니다.

5. 핵심 기능 스펙

MVP에서 “해야 하는 일”과 “원본에서 따라온 것”을 구분합니다.

기능 상태 설명
학교 코드 대문 핵심 코드 → 학교 판별 → httpOnly 쿠키 세션
학교별 테마 UI 핵심 색·교훈·설립연도·로고 반영
발명 키워드 검색 핵심 제목·요약 등 inventions 조회 (원본과 동일 계열)
문제유형 / SCAMPER 필터 핵심 발상 기법·문제 태그로 결과 좁히기
발명 상세 핵심 문제·해결·도면·태그 등
특허 검색식 / KIPRIS 핵심 선택 발명 기반 특허 탐색
관리자 / 파트너 모집 원본 잔존 sdg2에서 같이 복사된 영역. High MVP의 주인공은 아님
학교별 DB 완전 분리 미완 현재는 “입장·UI만 학교별”. 데이터 격리는 후속 과제

6. 개발 관점 특징

이 프로젝트가 “어떻게 설계되어 있는지” 성격 정리.

잘 된 / 의도된 점

  • 파생 MVP 전략 — 검증된 검색 제품을 복사해 학교 게이트만 얹음. 속도가 빠름.
  • 테마 = 설정 파일 — 학교 추가 시 프로필·코드·로고만 늘리면 됨.
  • 서버 세션 — httpOnly 쿠키 + HMAC 서명 토큰.
  • middleware 가드 — 화면 URL과 API를 같이 막음.
  • App Router — 레이아웃에서 학교 세션을 읽어 CSS 변수까지 서버에서 주입.

신입이 기억할 패턴

  • Config-driven UI — 하드코딩 대신 schools.ts
  • Gate → Session → Theme — 입장 → 기억 → 옷 입히기
  • BFF 느낌의 API Route — 브라우저가 DB에 직접 안 가고 Next API를 경유
  • 원본 스키마 존중 — PRD상 Supabase 구조를 크게 안 건드림

7. 취약점 · 리스크 · 기술 부채

“지금 약한 곳”을 솔직히 적어 둔 섹션입니다.

항목 심각도 왜 문제인가 개선 방향(힌트)
학교 코드가 코드베이스에 존재 중 school-codes.ts는 서버 import 용도지만, 저장소·빌드 산출물에 노출될 여지가 있음. 코드도 짧고 추측 가능(MIRAE 등). 환경변수/DB의 access_codes로 이전, 강한 랜덤 코드, rate limit
데이터 미분리 고 학교 세션이 있어도 검색은 공통 inventions를 볼 수 있음. “그 학교 데이터만”이라는 제품 약속과 어긋날 수 있음. 학교별 DB/스키마 또는 invention에 school 키 + RLS
원본 기능 잔존 중 admin, test 페이지, 파트너십, 채팅 등 MVP 범위 밖 코드가 남아 공격면·유지비·혼란이 커짐. High용으로 라우트 정리·비활성·권한 재점검
브루트포스에 약할 수 있음 중 대문 코드 입력을 막는 횟수 제한·캡차가 약하면 짧은 코드를 반복 시도 가능. IP/세션 rate limit, 실패 잠금, 긴 코드
테스트 커버리지 얇음 낮~중 학교 코드 정규화 등 일부 단위 테스트만 존재. 회귀에 취약. 인증·middleware·검색 가드 e2e 추가
시크릿·키 관리 중 Supabase anon key, ADMIN/SCHOOL_SESSION_SECRET, KIPRIS 키 등이 .env에 의존. 유출·원본 DB 공유 혼동 주의. 환경 분리(staging/prod), 키 로테이션, 최소 권한
가장 중요한 한 줄: 지금 High는 “학교별 교문과 교복(UI)”은 갖췄지만, “학교별 창고(데이터)”는 아직 완전히 나뉘지 않았을 수 있습니다. 데모·파일럿 전에 이 약속을 제품/보안 기준으로 다시 확인해야 합니다.

8. 신입용 용어집

회의에서 자주 나오는 말만 짧게.

MVP
최소 기능 제품. 일단 써볼 수 있게 핵심만 만든 버전.
App Router
Next.js에서 src/app 폴더 구조로 페이지·레이아웃을 구성하는 방식.
middleware
요청이 페이지/API에 들어가기 전에 가로채서 “통과/차단/리다이렉트”하는 문지기.
httpOnly 쿠키
브라우저 JavaScript가 읽지 못하게 한 쿠키. XSS로 세션 훔치기 난이도를 올림.
HMAC 서명 토큰
서버 비밀키로 내용에 도장을 찍은 티켓. 위조하면 검증에 실패.
Supabase
PostgreSQL DB + API를 쉽게 쓰는 백엔드 서비스.
SCAMPER
아이디어 발상 기법(대체·결합·응용 등). 이 서비스의 필터 축 중 하나.
KIPRIS
한국 특허정보 검색 서비스. 발명 → 특허 검색식으로 연결.
RLS
Row Level Security. DB가 “이 사용자는 이 행만” 보게 강제하는 장치.
기술 부채
나중에 갚아야 할 설계/코드 숙제. 지금은 빨리 가려고 남겨 둔 것.

9. 자주 받는 질문 → 답변 예시

Q. 이거 모바일 앱이에요?

아니요. 반응형 웹입니다. 폰 브라우저에서도 열리게 만든 웹 서비스예요.

Q. 백엔드 서버를 따로 두었나요?

전통적 Spring 서버를 따로 두기보다, Next.js API Route + Supabase 조합입니다. 화면과 API가 같은 저장소에 있습니다.

Q. 학교마다 사이트를 네 개 만들었나요?

아니요. 사이트는 하나이고, 코드에 따라 테마와 세션만 갈라집니다.

Q. 원본 IdeaPrism이랑 뭐가 달라요?

검색·상세·특허의 뼈대는 같고, High는 고등학교 4곳 전용 대문 + 학교 브랜딩에 초점을 맞춘 버전입니다.

Q. 지금 바로 학교 현장에 넣어도 되나요?

파일럿은 가능하지만, 데이터 격리·코드 강도·불필요 라우트 정리·키 관리를 점검한 뒤 본배포하는 편이 안전합니다. (위 취약점 섹션 참고)
