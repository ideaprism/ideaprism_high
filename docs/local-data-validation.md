## 발견 후 수정한 사항

- 공개 학교 공용 코드는 인증 경로에서 제거하고, 관리자가 발급한 계정에 학교를 필수 연결했다.
- 코드 변경/비활성화에 세션 버전을 적용해 기존 쿠키를 재사용할 수 없게 했다.
- 카탈로그의 위생·환경(오염)·S(대체) 등 현재 표기를 사용한다.
- 상세의 학생명과 원본 학교·학년을 표시한다. `grade_year`에 이미 포함된 '학년'을 중복으로 붙이지 않는다.
- 특허 화면은 패키지 검색어를 받은 뒤 완성된 검색식으로 첫 요청을 보낸다. 없는 Simple/Expert 자료를 만들지 않는다.
- 실제 브라우저에서 발견한 Next.js loopback 호스트 정규화 문제를 수정했다. 동일 출처 판단은 실제 Host와 프로토콜을 사용하며, 공격자 Origin·다른 포트·다른 프로토콜은 계속 거부한다. 실패 재현 테스트를 먼저 추가한 후 통과를 확인했다.

## 로컬 운영 상태

최종 프로덕션 서버는 `http://127.0.0.1:3102`에서 실행 중이다. 서버 시작 시 모든 Supabase 환경변수를 빈 값으로 지정했다. Node/Edge 브라우저 검증은 이 PC에서 실행했고, 브라우저 외부 네트워크 요청은 차단했다. KIPRIS 요청은 애플리케이션 서버의 기존 외부 API 경로로 확인했다.

초기 관리자 코드: `private/initial-admin-code.txt`. 계정 데이터: `private/accounts.sqlite`. 테스트에서 발급한 계정은 모두 비활성화했다. 대표자가 사용할 학교 계정은 관리자 `/admin/codes`에서 발급한다. 자격증명·계정 DB·전체 데이터 패키지는 Git에 포함하지 않는다.

SQLite는 영구 디스크를 가진 Node 서버용이다. 여러 인스턴스 또는 서버리스 배포는 별도 저장소 설계가 필요하다. Node 22.16의 SQLite experimental 경고는 출력되며, 저장소 접근을 막는 오류는 없었다. 기존 전체 저장소 린트 누적 이슈를 정리한 작업은 아니며, 변경 핵심 파일을 대상으로 린트를 실행했다.

## 후속 수정: 학교 코드 변경 후 로그인 실패

초기 검증에서 남겨둔 비활성 학교 계정 네 개의 코드를 사용자가 변경했다. 코드 저장은 성공했지만 비활성 상태가 유지되어 네 학교 모두 로그인 401을 반환했다. 관리 화면이 비활성 계정에도 '다음 로그인부터 사용'이라고 안내한 것이 문제였다.

- 해당 네 계정만 기존 코드와 학교 연결을 보존해 활성화했다. 관리자 코드는 변경하지 않았다.
- 관리 화면에 서버와 동일한 기준의 로그인 가능/불가 상태를 표시한다. 비활성 계정에는 경고와 '코드만 저장', '저장하고 활성화'를 구분해 제공한다.
- 저장 API가 실제 로그인 가능 여부를 반환하고, 안내 문구는 그 결과를 따른다. 학교 로그인 화면도 비활성 계정을 별도로 안내한다.
- 이후 검증 스크립트는 해당 실행에서 만든 임시 계정만 삭제한다. 기존 사용자 계정은 정리 대상으로 삼지 않는다.
- 서버 테스트 90개, 타입 검사, 프로덕션 빌드 통과. 실제 네 학교 코드로 브라우저 로그인, 검색 건수(167/82/70/5), 학생명·사진, 타학교 상세·사진 404를 확인했다.
- 별도 임시 계정으로 비활성 코드만 저장 → 로그인 차단 안내, 저장하고 활성화 → 새 코드 로그인, 활성 코드 변경 → 옛 세션 차단·새 코드 재로그인까지 검증했다.

실제 결과: [school-code-recovery-validation.json](school-code-recovery-validation.json). 모바일 수정 화면은 `private/school-code-validation/`에 보관했다.

외부 브라우저 플러그인에 실제 관리자 코드를 전달하는 호출은 자동 승인 검토에서 거절되어 실행되지 않았다. 이후 로컬 Node가 파일을 읽고 로컬 Edge에서 localhost로만 입력하는 방식으로 전환해 브라우저 검증을 완료했다.
