# Revise → High 통합 검증 기록

기록일: 2026-11-02. **공통 기능 통합과 로컬 검증은 완료. 실제 관리자 DB 연결 검증은 서버 키 설정을 기다리는 상태다. 운영 배포는 하지 않았다.**

## 변경 기준과 범위

- Revise 검토 기준: `043f2b4`, 브랜치 `codex/revise-review`.
- High 원본 보존 기준: `48fbb38`, 작업 브랜치 `codex/high-revise-integration`.
- 사용자는 최초 통합 계획 실행을 승인했고, 작업 중 관리자 대시보드도 유지·수정하도록 요청했다.
- 학교 프로필/코드, 교표 파일, SchoolProvider/SchoolCrest, 학교 홈, 학교·관리자 쿠키를 함께 지우는 로그아웃을 보존했다.
- High의 외부 node_modules 연결을 해제하고 독립 설치했다. 연결 대상인 ideaprism_2026의 의존성은 변경하지 않았다.

## 반영한 공통 개선

- 문장·Boolean 검색과 관련도 정렬, 복합 필터/패싯, 검색창 이동·강조.
- 검색 입력 타입·길이·상한·구문 검증, 일부 조회 실패 및 최대 후보 수 표시, 동일 검색어 재검색과 취소 가능한 제한 재시도.
- 상세 모달을 열 때 본문만 별도 조회하는 API와 상태 표시.
- KIPRIS 그룹 연산 보존, 잘못된 IPC/복합식 거부, 여러 단어 키워드 인용, 실제 조회식/IPC 해제 표시, 전체 timeout과 502/504 구분.
- Next 15.5.28, React 19.2.9, 동반 보안 패치 및 타입 검사 활성화.

## High 인증과 화면

- 네 학교의 학교명·교훈·색상·교표를 유지했다.
- SCHOOL_SESSION_SECRET을 관리자 키와 분리했다. 토큰의 audience, 서명, 정확한 두 구간, 정수 만료 시각을 검사한다.
- middleware와 API 핸들러가 모두 학교 인증을 검사한다. 상세 API와 정확한 `/api/chat` 경로도 포함한다.
- 상세 API는 `private, no-store`이며 학교 응답에 공유 캐시를 쓰지 않는다.
- 익명 검색어 Analytics 전송은 포함하지 않았다. High는 noindex/robots 차단이 기본이고, 공개 서비스의 canonical 도메인을 복사하지 않았다.
- 학교 인증 12시간/관리자 인증 8시간과 실제 제공 기능에 맞게 고지를 조정했다.

## 관리자 기능

- `/admin-login`에서 기존 관리자 기관의 활성 코드만 허용한다. 학교 코드·학교 쿠키는 관리자 권한을 주지 않는다.
- 서버 전용 Supabase 키로 코드 목록·발급·변경·활성화 및 기존 문의 조회를 처리한다. 브라우저의 비공개 DB 직접 접근을 제거했다.
- 관리 화면은 HttpOnly 쿠키와 DB 권한으로 진입한다. 새 로그인은 원문 관리자 코드를 sessionStorage에 저장하지 않는다.
- 각 요청에서 코드·기관의 활성 상태와 만료를 다시 확인한다. 비활성화된 코드의 기존 쿠키도 거절한다.
- 유한 횟수 코드는 로그인 때 조건부 UPDATE로 1회 사용한다. 마지막 허용 로그인 세션은 유지하고 다음 로그인을 제한한다. 동시 마지막 사용 요청은 200/409로 처리한다.
- 신규 기관 ID를 INSERT 전에 생성해 응답 유실 시에도 해당 기관만 정리한다. 중복/입력 오류/없는 행을 성공으로 표시하지 않는다.
- 실제 기관/코드/대기 문의 건수를 표시한다. 예시 검색량·인기 키워드·가짜 로그를 제거했다.
- 공용 DB의 기관 코드와 High 네 학교 진입 코드는 서로 별개임을 화면에 표시했다.
- 이전 화면에 연결되지 않은 문의 자동 승인·AI 최적화 프로토타입은 410으로 유지한다. 기존 문의는 조회만 제공한다.

## DB와 환경

- 기존 공용 Supabase 프로젝트의 스키마와 RLS/권한을 읽기 전용으로 확인했다. 실제 DB INSERT/UPDATE/DELETE나 마이그레이션은 실행하지 않았다.
- 발명/분류 테이블은 읽기 허용, 비공개 기관·코드·문의·bot_settings는 anon/authenticated 접근 차단, exec_sql 계열 실행 권한 회수 상태다.
- 서버 role의 기관·코드·문의 조회/쓰기 권한은 존재한다. 관리자용 API 키만 로컬에 아직 없다.
- 로컬 시스템 인증서는 `node --use-system-ca`로 사용했다. TLS 검증을 끄지 않았다.
- 최신 `sb_secret_*`는 apikey만, 기존 service_role JWT는 Bearer를 함께 사용한다. [Supabase 공식 안내](https://supabase.com/docs/guides/getting-started/api-keys#known-limitations)

## 남은 확인 및 운영 제한

1. 사용자가 `.env.local`에 SUPABASE_SECRET_KEY 또는 SUPABASE_SERVICE_ROLE_KEY를 설정하면 실제 High 서버를 재시작한다. 키는 커밋하거나 채팅에 출력하지 않는다.
2. 실제 관리자 로그인·읽기·기관/코드 현황 일치를 확인한다. 운영 코드 변경/발급의 임의 테스트 데이터는 만들지 않는다. 쓰기 경로의 실패/중복/경합은 모의 테스트로 검증했다.
3. 배포는 별도 단계다. High 전용 학교 세션 키와 관리자/DB/KIPRIS 설정, 방화벽 로그인 시도 제한을 배포 환경에 반영한다.
4. 관리자 앱 내 제한은 프로세스별 분당 10회다. 공유 학교 코드는 개인 계정이나 학교별 데이터 소유권 분리가 아니며 학교 로그인에 분산 시도 제한은 없다.
5. 기관/코드 발급의 여러 REST 요청은 하나의 DB 트랜잭션이 아니다. 프로세스 강제 종료·연속 네트워크 장애 시 정합성 확인이 필요하다.
6. 기존 lint 부채: Revise `src` 오류 39/경고 55, High `src` 오류 28/경고 44. 주로 기존 테스트 페이지, 공용 표시 컴포넌트, Supabase/특허 유틸의 any·기존 규칙 위반이다. 수정 범위 lint는 오류 0이며 전체 lint 통과로 보고하지 않는다. 개발 의존성의 전체 audit 17건은 별도 정리 대상이다.

## 복구 기준

원본 High는 `48fbb38`, 검토된 Revise는 `043f2b4`로 보존되어 있다. 작업 브랜치 커밋을 기준으로 되돌리거나 별도 브랜치에서 비교한다. DB 변경은 없으므로 DB 롤백은 필요 없다. 학교 세션 서명 규칙 변경으로 이전 쿠키는 재로그인이 필요하다.
